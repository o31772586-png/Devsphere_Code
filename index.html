02

Devsphere Code LIVE – مواصفات المنتج

الفصول الافتراضية

منظومة فصول افتراضية مدمجة داخل Devsphere Code تتيح المحاضرات التفاعلية والبث التعليمي، وتعمل على الويب وتطبيق الهاتف.

Interactive Classroom

المدرس والطلاب يشاركون بالصوت والصورة وفق صلاحيات يحددها المدرس.

Broadcast Classroom

المحاضر يبث، والطلاب يشاهدون ويتفاعلون عبر المحادثة ورفع اليد.

Automatic Recording

تسجيل تلقائي وفق سياسة الأكاديمية والموافقات.

Optional Recording

المدرس يبدأ أو يوقف التسجيل إذا سمحت السياسة.

الوظائف داخل الفصل

  • صوت وصورة بجودة متكيفة ومشاركة شاشة.
  • سبورة تفاعلية وعرض ملفات وعروض تقديمية.
  • محادثة ورفع يد وأسئلة واستطلاعات قصيرة.
  • مضيف ومساعد مدرس ومشاركون بصلاحيات مختلفة.
  • غرفة انتظار وكتم وإزالة وإبلاغ وإدارة سلوك.
  • تسجيل المحاضرة ومعالجتها وإضافتها إلى مكتبة الطالب المصرح له.
  • إعادة الاتصال عند انقطاع الشبكة ومؤشرات جودة الاتصال.

محرك الاتصال (Connectivity Engine)

الاختيار التقني الأساسي هو LiveKit كـ WebRTC SFU، مع Provider Adapter داخل Backend لتقليل الارتباط بمزود واحد. يمكن تشغيل LiveKit Cloud في البداية ثم إضافة Self-hosted في بيئة مستقلة بعد اختبار الأداء والتكلفة.

Devsphere Code Web / Flutter (واجهات الطالب والمدرس)
↓
NestJS Backend (الهوية - التسجيل - الصلاحيات - إصدار الرموز + Webhooks)
↓
LiveKit Cloud (خدمة سحابية مدارة) ⇄ Self-hosted LiveKit (بيئة خاصة مستقلة)
↓
Private Recording Storage (تسجيلات خاصة ومحمية وروابط مشاهدة مؤقتة)
03

Devsphere Code LIVE – دورة التشغيل والأدوار

الصلاحيات والحضور
الدور الصلاحيات الأساسية
Owner / Adminإعداد السياسات، جدولة المحاضرات، تعيين المدرسين، مراجعة السجلات.
Teacher / Hostبدء وإنهاء الفصل، مشاركة المحتوى، إدارة المايك والكاميرا، التسجيل وفق السياسة.
Moderatorإدارة المحادثة والمشاركين والبلاغات وفق تفويض محدد.
Studentالانضمام للمحاضرة المصرح بها، المشاهدة، السؤال، رفع اليد.

تسلسل المحاضرة

  1. إنشاء المحاضرة وربطها بكورس ومدرس ومجموعة طلاب.
  2. التحقق من صلاحيات المدرس وجدول الكورس.
  3. إنشاء غرفة لدى مزود البث وتخزين معرفها.
  4. إشعار الطلاب قبل الموعد.
  5. الطالب يطلب الانضمام، ويتحقق Backend من الحساب والتسجيل والحظر والتوقيت.
  6. إصدار رمز اتصال قصير العمر وبأقل صلاحيات.
  7. بدء التسجيل إذا كانت السياسة والموافقات تسمح.
  8. إنهاء الجلسة ومعالجة التسجيل وتحديث الحضور والتقارير.
قاعدة أمنية: رابط المحاضرة وحده لا يمنح حق الدخول. كل طالب يحصل على صلاحيات من Backend بعد التحقق من التسجيل في الكورس وحالة الحساب وسياسة الجلسة.

الحضور والخصوصية والتسجيل

  • الحضور: يسجل النظام وقت الانضمام والخروج وإعادة الاتصال ومدة الاتصال الفعلية. لا يعتبر فتح الرابط حضورًا كاملاً، وتحدد الأكاديمية معيار احتساب الحضور وتتيح للمدرس مراجعة الحالات الاستثنائية.
  • الخصوصية والتسجيل: يظهر إشعار واضح قبل التسجيل، وتُجمع الموافقات اللازمة بحسب سياسة الأكاديمية والقانون. تسجل موافقة المستخدم وإصدار السياسة والتوقيت. يجب توفير بدائل مناسبة وإجراءات خاصة بالقصر عند انطباقها.

قواعد تصميم البيانات

  • UUID للمفاتيح الأساسية و Foreign Keys للعلاقات.
  • كل سجل مؤسسي يحمل tenant_id، مع تحقق من تطابق المؤسسة بين الجداول.
  • قيود فريدة لمنع تكرار غرفة المزود وأحداث Webhook.
  • فهارس على tenant_id, session_id, user_id, status, scheduled_start.
  • أوقات UTC باستخدام TIMESTAMPTZ، مع عرض توقيت الأكاديمية للمستخدم.
  • لا تحفظ مفاتيح LiveKit السرية أو رموز الاتصال طويلة الأجل في قاعدة البيانات.
  • سياسات احتفاظ وحذف للتسجيلات والمحادثات وسجلات الجودة.

منطق إصدار رمز الانضمام (Join Token Logic)

  1. قراءة هوية المستخدم من جلسة موثقة، وليس من body.
  2. التحقق من tenant و Enrollment وحالة المحاضرة.
  3. تحديد الدور المسموح به (Host / Moderator / Student).
  4. إنشاء Token قصير العمر بأقل grants لازمة.
  5. إرجاع عنوان الاتصال والرمز ووقت الانتهاء فقط.
  6. تسجيل عملية الإصدار دون تسجيل الرمز نفسه.

06

خطة الحماية والأمن

Defense in Depth

الحماية متعددة الطبقات، ولا يوجد نظام يمكن ضمان تأمينه بنسبة 100%. الهدف هو تقليل سطح الهجوم، ومنع الوصول غير المصرح، واكتشاف الحوادث والاستجابة لها.

الطبقة الضوابط الأمنية
IdentitySSO مع Devsphere Code، MFA للإدارة والمدرسين، جلسات آمنة، إبطال الجلسات.
AuthorizationRBAC + Tenant Guard + التحقق من التسجيل في الكورس على الخادم.
Live Tokensقصيرة العمر، أقل صلاحيات، لا أسرار في Web أو Flutter، منع مشاركة الصلاحيات.
TransportHTTPS/WSS, DTLS-SRTP وفق إعداد WebRTC، وإعداد TURN عند الحاجة.
Networkجدار ناري، منافذ ضرورية فقط، شبكات خاصة للخدمات وقواعد البيانات.
StoragePrivate Bucket، تشفير أثناء النقل والتخزين، Signed URLs قصيرة العمر.
AbuseRate Limits، انتظار، كتم وطرد وحظر، إبلاغ ومراجعة Moderation.
Auditسجلات إدارية ومراقبة محاولات الدخول والتغييرات الحساسة.
Operationsتحديثات دورية، نسخ احتياطي مشفر، اختبار استعادة، تنبيهات ومراقبة.

التسجيل والتشفير

تشفير النقل والتخزين مطلوب للتسجيلات. يجب التمييز بين تشفير النقل و E2EE؛ تسجيل الخادم يتطلب وصول خدمة التسجيل إلى الوسائط لذلك لا يجوز الادعاء بتوافق تسجيل الخادم مع E2EE كامل لا يستطيع الخادم فك تشفيره. أي وضع E2EE يقدم كميزة منفصلة مع قيود واضحة.

مكافحة تسريب المحتوى

  • علامة مائية باسم الطالب أو معرفه عند عرض التسجيل وفق سياسة الخصوصية.
  • روابط مشاهدة مؤقتة والتحقق من الصلاحية عند كل طلب.
  • تسجيل أحداث المشاهدة والتنزيل المسموح به.
  • عدم إتاحة الملفات عبر Public URLs.
  • تنبيه: لا يمكن ضمان منع تصوير الشاشة بجهاز خارجي أو كل طرق تسجيل الشاشة.

خصوصية الطلاب والقصر

إشعار التسجيل والموافقة وسياسة الاحتفاظ والحد الأدنى من البيانات، ووسيلة بديلة عند الحاجة، وإجراءات بلاغات وإشراف مناسبة. لا تستخدم تحليل الوجه لقياس الانتباه أو استنتاج حالة نفسية.

07

Hybrid Hosting والتشغيل

البنية التحتية والمراقبة

LiveKit Cloud (المرحلة الأولى)

إطلاق أسرع وتقليل عبء تشغيل البنية.

Self-hosted (مرحلة لاحقة)

تحكم أكبر بعد دراسة التكلفة والأداء والامتثال.

سياسة التوجيه (Routing Policy)

  • تحدد بيئة كل محاضرة وقت الإنشاء، وتخزن في live_rooms. لا يتم نقل غرفة نشطة بين مزودين أثناء انعقادها.
  • تستخدم Provider Adapter لتوحيد أوامر إنشاء الغرف والتسجيل وإنهائها.
  • يتم اختبار سعة الخادم ومناطق الاتصال قبل تحويل أحمال حقيقية إليه.
  • خطة تعافي واضحة: لا يعد الانتقال بين السحابة والخادم الخاص انتقالاً بلا انقطاع.

مراقبة التشغيل

المؤشر ما تتم مراقبته
Availabilityتوفر واجهات API وغرف الاتصال.
Connection Qualityزمن التأخير وفقد الحزم وإعادة الاتصال.
Recordingبدء التسجيل وفشله ومعالجته وتخزينه.
Securityمحاولات الدخول الفاشلة والأحداث المشبوهة.
Capacityالمشاركون المتزامنون واستهلاك CPU / Network.
Costساعات الاستخدام والتسجيل والتخزين ونقل البيانات.

خطة النسخ الاحتياطي والاستعادة

  • نسخ احتياطي دوري لقاعدة البيانات مع تشفير وفصل صلاحيات.
  • سياسة احتفاظ متعددة المستويات واختبار استعادة فعلي.
  • تخزين أسرار الإنتاج خارج المستودع البرمجي.
  • توثيق إجراءات Incident Response ومسؤوليات الفريق.

قواعد الدفع والإدارة المالية

  • لا تفعّل الكورس اعتماداً على صفحة نجاح المتصفح وحدها؛ تحقق من Webhook server-to-server والتوقيع والمبلغ والعملة، واستخدم Idempotency لمنع التكرار.
  • حالات الدفع: Pending و Processing و Paid و Failed و Cancelled و Refunded و Partially Refunded.
  • نفّذ Reconciliation بين المنصة والمزود والبنك، ولا تخزن بيانات البطاقة الحساسة.
  • مزود الدفع: Kashier مرشح أساسي مبدئياً، و Fawry Pay تكامل إضافي إذا لم تتوفر وسيلة فوري المطلوبة لدى المزود الأساسي. يجب تأكيد وسائل الدفع والرسوم والتسوية والاعتراضات كتابة. (وثائق Kashier: https://developers.kashier.io/docs/accept-payments | الأسعار: https://www.kashier.io/pricing)
  • إدارة مالية: افصل الإيراد الإجمالي عن صافي التحصيل والرسوم والعمولات والخصومات والضرائب. سجل كل Refund و Chargeback و Settlement. أنشئ كشفاً لكل مدرس في Marketplace. تتبع Gross Sales و Net Revenue و Payment Success Rate و Refund Rate. لا تخلط مستحقات المدرسين بأموال الأكاديمية دون Ledger واضح.

03

SRS – حالات الاستخدام وقواعد العمل

ملحق التطوير التنفيذي | 4

إنشاء المحاضرة

  1. المدرس أو المدير يرسل بيانات الكورس والموعد والنمط وسياسة التسجيل.
  2. الخادم يتحقق من صلاحية الدور وانتماء الكورس إلى Tenant نفسه.
  3. تنشأ جلسة بحالة Scheduled، ويُنشأ Room عند البدء أو وفق سياسة التهيئة.
  4. ترسل إشعارات للطلاب المسجلين في الكورس.

دخول الطالب

  1. الطالب يطلب Join Token من Backend بجلسة مصادق عليها.
  2. الخادم يتحقق من المستخدم و Tenant والتسجيل الفعال ووقت الجلسة والحظر.
  3. الخادم يصدر Token محدوداً قصير العمر لا يوقعه تطبيق الويب أو الهاتف.
  4. تُسجل أحداث الاتصال والحضور عبر أحداث المزود مع إزالة التكرار.

قواعد العمل وسياسات التسجيل

  • لا يثق الخادم في tenant_id أو role أو السعر أو حالة الدفع الواردة من العميل.
  • تغيير حالة الجلسة يتم عبر انتقالات مسموح بها فقط: Scheduled → Live → Ended أو Scheduled → Cancelled.
  • لا يمكن للطالب تشغيل التسجيل أو إدارة الغرفة.
  • لا تُعرض التسجيلات إلا بعد التحقق من صلاحية المشاهدة، ولا تستخدم روابط عامة دائمة.
  • الحضور لا يساوي الانتباه: مدة الاتصال ليست مقياساً قطعيًا للتركيز أو التعلم.
  • يمكن للمدرس مراجعة سجلات الحضور وتصحيح الأخطاء مع حفظ سجل التدقيق.
  • قاعدة أمان: كل قرار صلاحية يتم على الخادم. الواجهة تعرض ما يسمح به الخادم ولا تمنح الصلاحيات بنفسها.
  • سياسات التسجيل: تحدد الأكاديمية هل التسجيل تلقائي أو اختياري أو معطل. يجب إظهار إشعار واضح، وتسجيل الموافقات أو الأساس القانوني المناسب، وإتاحة البديل عند اللزوم، وتحديد الاحتفاظ والحذف والوصول. يراجع محامٍ مصري سياسة تسجيل الطلاب القصر والبيانات الشخصية قبل التشغيل.
